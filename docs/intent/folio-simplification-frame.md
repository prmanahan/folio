## 1. The direction, in one paragraph

folio's public pages become static files built by Astro from content files committed in folio's public repository. The content the AI reads is never in that repository and never in the shipped image: it is built by the job repository into a bundle, pushed to the running server, and held as a file on the Fly volume. The existing Rust/Axum binary on Fly serves the static pages, the AI endpoints, headers and redirects from one origin. Code and content release independently. The web admin and its password login go; a self-generated push token authorizes the one write path. Articles live on mnemra.dev; folio redirects to them and the AI sees summaries and links only. When private content is missing, the AI answers from public content; when no bundle is loaded at all, chat and fit are cleanly unavailable and pages are unaffected.

## 4. Option-space the derived specs may map

Nothing outside §2 enters a spec. Inside it, these are the spec-level decisions each spec owns. A spec that needs a direction not in §2 returns here (or to §7); it does not fill the gap.

**Astro page-side spec (`#3625`)** — the content-collection layout and strict schemas (the bundle spec hands it R-0014.1 and the config path for the private-key scan); the Dockerfile build stage; how `ServeDir` serves per-route HTML and a real 404 (fixes Sage F1); the layer ordering that puts headers on documents (fixes Sage F2, the same root cause as `#3491` and `#3493`); the article redirects as Axum 301s (Sage §4.2: Astro's own `redirects` emits meta-refresh under static output); the AI pane ported as islands; the page-side FAQ suggestions list (bundle spec D-4); the sitemap; `agents` as page files with avatar images in the repo (L-16); the projects-page content updates `#2626` and `#2830` become file edits via job (`#3470` msg 3, "and the projects updated"); CI gates (`astro check` replacing `svelte-check`; `#3488`); the operational choice in E-F3. **Two items this spec must design because the frame leaves them open:**
- **How job's generated page files reach folio.** Not ruled. Peter's words on `#3471`, said about the **private tier's** handoff, verbatim: *"keep it in job, just have a task to merge in a worktree with it. Trying to have the projects each have thier own puck and communicate vs implement directly. a worktree to be merged is a fine way to handoff IMO."* The first clause ("keep it in job") is RULED and is what L-4 cites. The worktree-handoff clause is **hedged ("IMO"), not ruled**, and was said of the private tier, not of page files — carried here as the preference to rank against, not as a direction. `#3471` records the mechanical constraint (a worktree belongs to one repository, so the crossing is a read into a folio worktree, not a job branch merged into folio) and three candidate shapes; the spec ranks them and puts the choice to Peter with a recommendation.
- **A reverse-path guard for generated page files** (L-4, QA-F13): hand edits in folio to files job generates must fail a check or be reported by the next generation, not drift silently.
